# Самопроверка ревьюером harness

Ты проверяешь изменение текущей ветки до PR. Простой режим: один агент поиска, механическая проверка находок, один проверяющий в свежем контексте. Полный режим (для изменений риска 2 или по просьбе): несколько агентов поиска с разным фокусом, механическая проверка со склейкой, несколько проверяющих и порог голосов. Это самопроверка: её итог ворота не принимают, его переносят в раздел «Проверено» PR. Файлы проекта не меняй, пока человек не попросит исправить находки.

Аргументы: `$0` — база (ветка или коммит), `$1` — фокус поиска (логика, безопасность, данные, конкурентность, обработка ошибок), `$2` — режим: `simple` или `full`; все необязательны. Режим можно дать и без фокуса: если `$0` или `$1` — ровно `simple` или `full`, это режим, а не база или фокус (`/harness-review full`, `/harness-review main full`).

Каждую команду запускай отдельным вызовом из корня проекта, ровно в том виде, как она написана ниже: без `cd`, `;`, `&&`, `|`, `$(...)` и переменных оболочки. Так её пропускают без вопросов: команды `git` из шагов ниже Claude Code сам считает только читающими, `review-depth` разрешает этот скилл, а `findings check` — этот скилл и правило harness в `.claude/settings.json`; составную команду в режиме без вопросов отклонят.

## 1. Изменение и режим

1. База — `$0`, если задана. Иначе ветка по умолчанию: `hosting.default_branch` из `harness.config.yaml` (после отсоединения — из `scripts/verify.config`), а если её там нет — `main`. Если есть `origin/<ветка>`, бери её.
2. Точка ветвления: `git merge-base HEAD <база>` — подставь в следующие команды выведенный хеш. Изменение — `git diff <точка>`: коммиты ветки и незакоммиченные правки; список файлов — `git diff --stat <точка>`. Новые неотслеживаемые файлы покажет `git status --porcelain`; они тоже часть изменения.
3. Если изменений нет — скажи «нечего проверять» и остановись.
4. Режим. Если `$2` (или, как сказано выше, `$0` или `$1`) — `simple` или `full`, это и есть режим. Иначе узнай риск изменения командой рантайма сразу, до запуска субагентов:

   ```bash
   node harness/core/runtime.mjs review-depth --json --base <база>
   ```

   Она отвечает JSON `{ "risk", "depth", "settings": { ... }, "full": { "search", "verify", "threshold" }, ... }`: уровень риска изменения по документу рисков базы, глубина конвейера для него и числа полного режима (глубина риска 2). `risk: 2` — полный режим, иначе простой. Ошибка команды (неизвестная команда — рантайм проекта старее скилла, тогда поможет `harness-kit upgrade`; битый документ рисков) — простой режим; назови причину в отчёте.
5. Числа полного режима — из `full` этого ответа: `search` агентов поиска, `verify` проверяющих, порог `threshold`. Если режим `full` задан аргументом, всё равно запусти команду ради чисел; при её ошибке — 5 агентов поиска, 3 проверяющих, порог 2.

## 2. Поиск

Простой режим: запусти субагента `harness-review-search` один раз. В задаче передай: точку ветвления и команду diff (`git diff <точка>`), список изменённых и новых файлов, фокус `$1`, если он задан. Субагент вернёт JSON `{ "findings": [...] }`.

Полный режим: запусти `search` субагентов `harness-review-search` параллельно и дождись ответа каждого. Ответ агента, который не JSON `{ "findings": [...] }`, не смешивай с остальными: запусти этого агента ещё раз и попроси вернуть только JSON; второй сбой — сообщи о нём и остановись (неполный поиск не даёт итога «чисто»). Агенту номер `i` (с нуля) дай фокус номер `i` по кругу из списка: логика; безопасность; данные; конкурентность; обработка ошибок. Фокус `$1`, если задан, добавь каждому. Список файлов каждому агенту сдвинь на его номер: агент `i` начинает обход с файла `i` по кругу. Остальное в задаче — как в простом режиме.

## 3. Механическая проверка

Передай находки командой рантайма harness — JSON одной строкой в одинарных кавычках (одинарную кавычку внутри JSON запиши как `'\''`):

```bash
node harness/core/runtime.mjs findings check --json --findings '<JSON { "findings": [...] } одной строкой>'
```

В полном режиме передай находки всех агентов поиска вместе и добавь в конец команды `--merge`: команда склеит одну проблему от разных агентов в одну находку и уберёт стилистику и то, что ловит CI.

```bash
node harness/core/runtime.mjs findings check --json --findings '<JSON находок всех агентов одной строкой>' --merge
```

Одна команда — короче 6000 символов: команду длиннее 10 000 символов Claude Code не разбирает, и правило разрешения на неё не действует. Если JSON длиннее, раздели находки на части, передай каждую часть отдельной командой в том же виде `{ "findings": [...] }` и сложи итоги частей. В полном режиме дели только по файлам: все находки одного файла — в одной части, иначе склейка их не увидит.

Команда отвечает JSON `{ "checked", "findings", "questions", "dropped" }`, а с `--merge` ещё `merged` и `filtered`. Здесь `findings` — находки, которые прошли проверку; `questions` — находки уровня «Предположение», они становятся вопросами автору; `dropped` — отброшенные с причинами; `merged` — сколько склеено; `filtered` — не публикуются, с причиной. Код выхода 2 и сообщение про `аргумент --findings` — переданный JSON не разобран: в простом режиме запусти агента поиска ещё раз и попроси вернуть только JSON (второй сбой — сообщи о нём и остановись); в полном режиме проверь, что собранная строка — один объект `{ "findings": [...] }` с одинарной кавычкой, записанной как `'\''`, и передай её заново. Другая ошибка (неизвестный флаг — рантайм проекта старее скилла, тогда поможет `harness-kit upgrade`; не репозиторий) или отказ в разрешении на команду — покажи сообщение и остановись, агентов поиска заново не запускай.

## 4. Проверка

Если в `findings` пусто — пропусти этот шаг. Иначе пронумеруй находки из `findings` с 1.

Простой режим: запусти субагента `harness-review-verify` один раз со всем списком и номерами. Он вернёт JSON `{ "results": [{ "id", "verdict", "reason" }] }`. Оставь находки с `verdict: "upheld"`. Находка с `refuted` или без ответа в отчёт как находка не попадает.

Полный режим: если `verify` равно 0, оставь все находки. Иначе запусти `verify` субагентов `harness-review-verify` параллельно, каждого со всем списком и номерами, и дождись всех. Находка остаётся, если `upheld` у неё не меньше порога `threshold`; ответ без этой находки — голос «против». Если проверяющий не ответил вовсе, а без его голоса исход находки не решён, находка непроверена: назови её в отчёте отдельно. Воспроизведение тестом в самопроверке не запускается.

## 5. Отчёт

Напиши отчёт по-русски, по убыванию серьёзности: сначала `Important`, затем `Nit`, затем `Pre-existing`. Для каждой находки: `file:line` и утверждение; уровень («Подтверждено» для `confirmed`, «Вероятно» для `likely`); дословная цитата; воспроизведение, если есть; что опровергло бы находку; в полном режиме — сколько проверяющих за. Затем вопросы автору из `questions`. В конце — сводка одной строкой:

`harness-review: Important N, Nit N, Pre-existing N; вопросов N; отброшено проверкой N, проверяющим N (база <база>).`

В полном режиме сразу за ней — вторая строка:

`harness-review: полный режим, риск N: поиск N, проверяющих N, порог N; склеено N, не публикуется N, непроверено N.`

Предложи перенести сводку и команду `/harness-review <база>` в раздел «Проверено» PR. Находки `Important` нужно исправить до PR; исправляй их, только если человек попросит.
